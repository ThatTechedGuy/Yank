Why three parts

ClipCore holds the rules and has no UI, so we can test it quickly without starting the app. ClipSystem holds the code that talks to macOS. It sits in the package too, so its tests also run without the app. The app holds what you see, and what only Xcode handles: signing and permissions.

Code architecture

Three rings; dependencies point inward; ports where our code meets macOS.

Our rings

This is Clean Architecture made small. There are three rings. Arrows mean "depends on". They always point inward.

One deliberate shortcut

Strict Clean Architecture would hide Store behind a "repository" protocol, in an outer ring. We don't. There is only one database. Tests use a real SQLite file in a temporary folder, which takes milliseconds. A protocol and a fake for it would add code, and the fake could drift from the real behaviour.

Ports: where our code meets macOS

A port is a small protocol. ClipCore defines it. The real app plugs in the macOS version. Tests plug in a fake. We only add a port where a test needs a fake. There are five.

PortReal version (ClipSystem)Fake version (tests)Why a fake is needed
ClipboardSystemClipboard, using NSPasteboardFakeClipboard: a list of prepared copiesTests must never read or change your real clipboard.
KeyPressingKeyPresser, using CGEventFakeKeyPresser: counts pressesA test must not type ⌘V into whatever app is open.
FrontmostAppFrontmostAppReader, using NSWorkspaceFakeFrontmostApp: returns a set app IDTests need to pretend a copy came from a password manager.
AccessibilityStatusSystemAccessibilityStatus, using AXIsProcessTrustedFakeAccessibility: allowed or notTests need both cases. Changing the real permission needs you.
LinkFetchingLinkFetcher, using LPMetadataProviderFakeLinkFetcher: records which links were asked forTests must not use the network. They must prove local links are never fetched.

Time is not a port. Code that needs the time takes a small function, now: () -> Date. Tests pass a fixed time.

PrivacyRules.swift (a sketch)
public struct PrivacyRules: Sendable {
    public static let markerTypes: Set<String> = [
        "org.nspasteboard.ConcealedType",
        "org.nspasteboard.TransientType",
        "org.nspasteboard.AutoGeneratedType",
        "com.agilebits.onepassword",  // 1Password's older marker, see nspasteboard.org
    ]
    public var ignoredApps: Set<String>
    public var ownMarker: String

    public func decision(types: [String], sourceApp: String?) -> CaptureDecision {
        if types.contains(ownMarker) { return .moveOwnPasteToTop }
        if !Self.markerTypes.isDisjoint(with: types) { return .skip }
        if let sourceApp, ignoredApps.contains(sourceApp) { return .skip }
        return .save
    }
}

How the parts talk

Saving a copy

Pasting an item

The paste stack, as states

Who runs where

Main thread

Runs the UI. It also checks the clipboard, reads from it, and writes to it when pasting. The clipboard (NSPasteboard) belongs to the main thread.

Store

Owns the database and the large-format folders. Nothing else writes to disk. Every Store call is async and does its work off the main thread, including the duplicate-key hash, so the main thread never touches the disk or hashes 200 MB.

Store uses GRDB's "database pool". Many reads can run at the same time as one write. GRDB does this work on its own threads. We only call its async functions, so the main thread just waits for the answer.

Background tasks

These run at low priority. They make small previews, read text in images (Vision) and fetch link previews (LPMetadataProvider). They save their results through Store.

Saving a copy

When the clipboard counter changes, we run the privacy checks first. They look for secret, temporary or auto-generated markers. They also look for ignored apps and for our own pastes.

Then we read each format, skipping any over 256 MB, and stop adding formats once the item reaches 1 GB. Then we give the data to Store. The steps are drawn under C8.

Very large copies (review fix 6)

Some apps, like Photoshop and Preview, only create the data when another app reads it. That can take several seconds.

In slice 1, we time a 200 MB image copy. If the main thread waits more than 50 ms, we read large formats in the background instead.

macOS hands over each format as one block. There is no way to ask its size first, or to read it in parts. So a format over 256 MB is still read in full, then dropped: the cap saves disk, not time or memory. While a very large copy is being read and saved, memory briefly goes above the usual limit. It drops back once the save is done. The duplicate key, a hash of the data, is computed inside Store, off the main thread.

Data

Storage

We use SQLite through GRDB.swift. GRDB uses the SQLite that comes with macOS, so search speed is the same. We write no low-level database code ourselves.

The database layout may change in later versions. GRDB's migrator tracks this. Each change is one named upgrade step, and it runs only once.

There is one database file. It lives in the app's sandbox folder: ~/Library/Containers/<bundle id>/Data/Library/Application Support/. It uses WAL mode, which lets reads and writes happen at the same time.

Small formats live in the database. Large ones live next to it (review fix 2, revised 7 Nov 2026). A format up to 1 MB is stored in its row. A larger format is written to Application Support/Formats/<item id>/<n>.bin, and its row stores that file name instead of the bytes. Text, links, colours and small images stay in the database. Big images and large formatted text go to the folder. File items store only the file's location, never its contents, so they always stay in the database.

Why not everything in one file, as the first review said: Time Machine copies a whole file when any part of it changes, and the database changes on every copy. With a multi-GB history inside it, every hourly backup would copy all of it again. VACUUM on a file that size needs the same amount of free disk and takes minutes. And SQLite's own advice puts the crossover between "store in a row" and "store as a file" near 100 KB; we use 1 MB so that only genuinely large data leaves the database.

What we keep from the first review: Store deletes an item's row and its folder in the same call, so deleting an item still removes all of it. If the app quits between the two steps, a sweep at launch removes any folder whose item is gone. Items never share data. The card preview lives in its own table, so paging the list never reads image bytes.

How we spot the same item (review fix 7)

Each item gets a "duplicate key". When you copy something again, the newest item with the same key moves to the top. The newer copy wins: Store replaces the item's formats and source app with the new copy's, keeps its ID, title and pinboard, and the Enricher makes its preview again. So what you copied last is what pastes. The key is not unique: Duplicate, New text item and "Save as new item" can create two items with the same content on purpose.

The key is a SHA-256 of the data. Store computes it off the main thread, so a 200 MB image never stalls the UI while it is hashed.

ItemIts key
TextA fingerprint (hash) of the plain text. So the same words from Safari and Terminal match.
ImageA fingerprint of the image data.
FilesThe file paths.
ColourThe colour value.

Safe search (review fix 1)

SQLite's search has its own special words and symbols. If you typed one, search could break.

GRDB has a helper for this, called FTS5Pattern(matchingAllPrefixesIn:). It turns any typed text into a safe search. Each word also matches longer words that start with it. All words must match. If nothing searchable is left, like an empty box or just *, every card shows.

You typeWhat happens
don'tFinds items that contain "don't".
"helloFinds items with words starting "hello". The stray quote does no harm.
meeting NOTFinds items with both "meeting" and "not". NOT is just a word here.
*Shows the full list.
sOne letter shows the full list. Search starts at two letters.

The slow case is the short query, not the long one: sa* matches a large share of 100,000 items, and SQLite then ranks all of them. So the search table is created with FTS5 prefix indexes for two and three letters (GRDB: prefixes: [2, 3]), and the 100,000-item timing test uses two- and three-letter queries.

Erasing history

Erasing deletes all items that aren't pinned, and their folders, in one step. Then it runs VACUUM in the background. VACUUM is SQLite's command to shrink the file. Because large formats live outside the database, the file stays small and VACUUM stays quick.

Code and test rules

House rules for the code

1 · Clear names

Follow the Swift API Design Guidelines. A call should read like a sentence: store.moveToTop(item). Booleans read as facts: isPinned.

2 · Code that reads without comments

Names carry the meaning. A comment explains only why, never what. Public ClipCore types get a one-line /// summary, because Xcode shows it in Quick Help. This is the one place where Apple's guidelines ask for more than your "no comments" rule.

3 · One job per type

If a type's description needs the word "and", split it.

4 · Values first

Data is a struct or enum. A class is only for things with identity: observed models and adapters. Shared state that changes lives in an actor.

5 · Safe threads

Build in Swift 6 mode with zero warnings. UI and models are @MainActor: the App target turns on Swift 6.2's "default actor isolation: MainActor" setting, so views and models need no annotation of their own; the two package modules keep the normal default. No DispatchQueue. No @unchecked Sendable without a one-line reason.

6 · Small public surface

Everything is internal unless another module needs it. Details are private. Classes are final.

7 · No hidden errors

Never use try? where data could be lost. Log the error with Logger. Show a message if you need to act.

8 · No force unwraps

No ! outside tests, except for constants that can't fail, like a fixed URL.

9 · Plain wiring

Pass dependencies in through init. AppModel creates everything once. No singletons of our own and no dependency-injection library.

10 · Debug-only code stays out

Test helpers like --seed live inside #if DEBUG. The app you use daily doesn't contain them.

11 · Formatting

Use swift-format, which comes with the Swift tools, so it adds no dependency. One config file in the project.

12 · Shortcuts are labelled

If we knowingly cut a corner, the code says so: // shortcut: what it can't do, when to fix it.

What we deliberately don't do

No protocol for every class. No mocking library: fakes are written by hand and stay small. No coordinator objects. No module per feature. No VIPER or TCA. Each of these would add files to read and keep in sync, with no problem in this app that they solve.

Unit, integration, or only end-to-end?

Short answer: all three, shaped like a pyramid. Plus checks by hand.

Most tests are fast unit tests. Some are integration tests that use real SQLite and real macOS services. A few are UI tests that drive the real app. The things no test can reach, like macOS permission prompts, are on the hand-test checklist.

Unit test

Tests one small piece of logic on its own. It uses no disk, no network and no windows. It takes about a millisecond.

Example: "a copy marked as secret is never saved."

Integration test

Tests our code together with one real outside thing. That might be a real SQLite file in a temp folder, or a real but private clipboard. It takes up to a second.

Example: "erasing history keeps pinned items and makes the file smaller."

UI test (end-to-end)

Launches the real app and clicks and types like a person. It takes several seconds. It can break for timing reasons.

Example: "typing in the search box filters the cards."

By hand

You follow the checklist in Part 1. This covers what automation can't do: permission prompts, pasting into other apps, other keyboards, screen recording.

Why not only end-to-end tests?

  • They are slow. 90 UI tests would take many minutes, so you would run them less often.
  • They are flaky. Window focus and timing make them fail for no real reason. Then people stop trusting them.
  • When one fails, it doesn't tell you where the bug is.
  • They still can't reach macOS permission prompts or other apps. You would check those by hand anyway.

Why not only unit tests?

  • A unit test with a fake can pass while the real code is wrong. For example, the SQL could have a typo, or the real clipboard could return data in another shape.
  • Integration tests catch these mistakes. They run against real SQLite and real macOS services, in a safe sandbox.

Rules for our tests

  • Put each test at the lowest level that can catch the bug.
  • A bug found by hand gets a test first, then a fix.
  • No sleeping in tests. Time comes from a fixed now.
  • Unit and integration tests never touch your real clipboard, real history or the network. UI tests drive the real app, so they do write to the general clipboard; scripts/test.sh says so before it starts.
  • scripts/test.sh quits the copy of the app you use daily before the UI tests, and reopens it after. Two copies would both poll the clipboard, both try to register ⇧⌘V (the second fails), and the daily copy would record the test's clipboard writes.
  • Test names describe behaviour, like markedCopiesAreNeverSaved.
  • Slow tests carry a .slow tag, so the quick run can skip them.

An integration test (a sketch)
@Test(arguments: ["\"hello", "don't", "c++", "NOT", "*", ""])
func searchNeverBreaks(typed: String) async throws {
    let store = try Store.inTemporaryFolder()
    try await store.save(.text("hello don't c++ NOT"))

    let rows = try await store.search(typed, .everything, limit: 10)

    #expect(rows.count == 1)  // a match, or the full list
}

GRDB's search helper turns typed words into a safe query. This test proves it works for every tricky input, against real SQLite.

Tests

The tests use Swift Testing and live in ClipCoreTests. Each test fails if its rule breaks (review fix 10).

1 · Privacy

Items marked secret, temporary or auto-generated are not saved. Neither are items from ignored apps. A normal copy is saved.

2 · Duplicates

The same text, with and without formatting, is saved once. Different text is saved twice.

3 · Safe search

Typing "hello, don't, c++, NOT, * or nothing at all causes no error. The results make sense.

4 · Erasing

Pinned items and their data are kept. Everything else is gone.

5 · Large formats

A 2 MB format is saved as a file and read back identical. Deleting the item removes its folder. A folder left behind by a crash is removed at the next launch.

Also · Timing

A test times two- and three-letter searches over 100,000 fake items, the slow case.

Slice 1

Save copies

Large

Goal: every copy you make is checked by the privacy rules and saved to the database. There is no panel yet. The menu shows how many items are saved.

Steps

  1. ClipCore model: Item, ItemSummary, Format, ItemKind, CapturedCopy.
  2. Rules: PrivacyRules, DuplicateKey, Snippet (first 200 characters, tidy spaces), and kind detection. A link is public.url on the clipboard, or plain text that is nothing but one http(s):// address (C1). File, image and colour come from their types. Anything else is text.
  3. Storage: GRDB records for the tables. Upgrade step 1 creates all five tables (items, formats, previews, pinboards, search). The search table uses GRDB's synchronize(withTable:), which keeps the index up to date by itself, and has prefix indexes for two and three letters (prefixes: [2, 3], see Storage). FormatFiles writes a format over 1 MB to Formats/<item id>/<n>.bin and reads it back; its row stores the file name. Then Store, built on a GRDB database pool, with save (insert, or move to top taking the new copy's formats and source app), items (newest first, in pages), count, and a launch-time sweep of folders whose item is gone. save computes the duplicate key, so the hash runs off the main thread.
  4. Ports: Clipboard and FrontmostApp.
  5. CaptureService: on each tick, compare the change counter, ask the rules, read, then save. It also reports the clipboard access state (next step).
  6. Clipboard access (moved here from slice 6): the first read triggers macOS's "paste from other apps" alert. The Clipboard port exposes accessBehavior. If it is Deny, or still Ask after the alert, the menu shows a message with a button that opens System Settings → Privacy & Security → Paste from Other Apps. The README says: choose Allow once.
  7. ClipSystem: SystemClipboard reads each format. A format over 256 MB is read, then dropped (macOS gives no size first; see Part 2). It stops adding formats once the item reaches 1 GB. FrontmostAppReader returns the app's ID.
  8. App: AppModel opens the Store and starts a 0.25-second timer with 0.025 seconds of tolerance, so macOS can group wake-ups. When the counter changes, a 0.3-second wait starts; a newer change restarts it. These are Paste's own values (Ghidra finding G1, G2). The menu shows "N items saved" for now.
  9. Measure: copy a 200 MB image from Preview. Time how long the main thread waits for the read (the hash is already off the main thread). Write down the decision: keep reading on the main thread, or move large reads to the background.

Tests

  • Unit: privacy rules for each marker and for ignored apps; duplicate key for text with and without formatting; snippet; kind detection, including a URL as plain text and a sentence that contains a URL (text, not link).
  • Integration: Store in a temp folder: save, save again moves to top and the item now has the second copy's formats and app, the search index row exists. A 2 MB format is saved as a file, read back identical, and its folder goes with the item; a stray folder is swept at launch. CaptureService with FakeClipboard and a real Store. SystemClipboard on a private named clipboard: write formats, read them back, the 256 MB and 1 GB limits.
